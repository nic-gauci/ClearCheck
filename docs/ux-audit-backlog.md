# ClearCheck UX audit and fix backlog

Audited the local preview on the `codex/signed-in-workspace` branch. The public pass covered the homepage, pricing, login, signup, confirmation and reset states, source and policy pages, and the checkout return screens. The signed-in Safari pass covered each sidebar destination, the client directory and queues, templates and integrations, all seven tabs on an existing client record, and saved match and incomplete results.

The audit inspected existing records and opened forms without saving. New screening submissions, actual email delivery, PDF downloads, document uploads, Stripe payments, and changes to settings or roles still need end-to-end verification. No product fixes were made as part of this audit.

## First implementation pass

- Incomplete zero-match wording now qualifies which sources were checked and names unavailable sources in the result and PDF. History qualifies its zero count. Verified the original incomplete result in Safari.
- EUR-Lex PDF routes now generate a PDF search fragment. The result offers **Open source document** and **Copy name**. Verified the corrected fragment and copy control on the original saved match in Safari. Automatic highlighting in individual PDF viewers still needs testing.
- The screening form collapses optional case details, shows the credit cost at the action, and puts the review editor after evidence. Source health now separates the publisher date, the successful EU download, and the latest status check, with an unavailable-source warning on the screening form.
- The new-client date field already started empty in code. Its label and helper now explicitly say that it is optional. Saving a blank test client to verify the Safari date picker still needs a test account or isolated environment.
- Credit policy and the remaining backlog are open.

## Second implementation pass

- Added a versioned screening write and billing policy. A completed official check costs one credit. An incomplete result remains in history and the audit trail with a zero charge. One available credit is still required to start a screening. Apply the new database migration before releasing the app branch. Existing screenings and their charges are historical records.
- Added the public sample with potential-match and incomplete modes and sample PDF export. Clarified beta pricing and policy wording, and adjusted the public hero and navigation to fit narrower viewports.
- Added an email-first password recovery screen and a separate signed-in password change form. The recovery form requires the recovery event instead of accepting an unrelated signed-in session.
- Added actionable dashboard source warnings and reviews due, linked history subjects, retained browser-back filters, grouped secondary history actions, and split profile and organisation saves.
- Added a client approval checklist, a dedicated reviews queue link, settings links for templates and integration coverage, internal request wording, actor labels in client activity, and a template preview.
- Missing checkout references now lead to purchase history. Pending payments can be retried, and test checkout is labelled near plan selection.

Verified with 40 application tests and two rollback-only SQL fixtures in isolated PostgreSQL. The fixtures cover repeated incomplete and complete screening charges, access denial, blank client review dates, templates, approval and audit behaviour, and organisation isolation. Browser checks covered the public sample modes, checkout recovery, and the password reset entry screen. Both sample PDF variants generated successfully in the test suite. A signed-in Safari walkthrough verified all sidebar destinations, the approval checklist, reopening an incomplete result, and restoring the Incomplete filter after returning to History.

Still open before release: deploy the database migration with the application, verify real email delivery and links in a test inbox, submit a new screening and exercise document uploads and PDF downloads in a test environment, run Stripe Checkout and webhook tests, verify a scheduled EU sync after the manual repair, and confirm an operator receives source-failure alerts. Verified operator details and monitored contacts must be supplied and approved before public launch.

## P0 — Result accuracy, credits, and trust

- [ ] **Make incomplete results impossible to misread. Reproduced in Safari.** Open a saved result with zero matches and only two of three official sources completed. The assessment warns against treating it as clear, but the metrics and findings still say “No official-list names matched.” Apply the same incomplete wording in the result, history, and PDF. A result with no matches should say “No matches on the two sources checked” and list the missing source. Verify all combinations of complete/incomplete coverage and zero/nonzero matches.
- [ ] **Define and implement a fair credit policy for incomplete checks. Confirmed in code.** The screening RPC deducts one credit for an incomplete saved result, and the UI tells the reviewer to retry. Decide between no charge for incomplete results and a free linked retry. Keep incomplete attempts in the audit trail. Verify the balance, displayed cost, and repeat submissions under the chosen policy. Align the screening form, billing copy, and terms.
- [ ] **Fix official evidence links and provide a dependable fallback. Reproduced in Safari.** Reopen a saved EU match with a EUR-Lex URL in the form `/legal-content/EN/TXT/PDF/?uri=…`. The link gets an HTML text fragment because the PDF classifier misses this path. Recognise the real EUR-Lex PDF format and test it alongside direct PDFs and ordinary webpages. Provide **Open source document** and **Copy name**, with a page jump where the page is known. Verify behaviour in Safari and a compatible PDF viewer. Treat scan-only PDFs and viewer limitations honestly.
- [ ] **Resolve beta access, operator identity, and support contradictions. Observed on public pages.** The homepage invites registration and advertises priced plans, while the privacy notice says public registrations and live payments remain disabled pending verified operator details and approval. Make access and payment availability consistent with the actual beta rules. Publish verified operator and monitored support, privacy, and security contacts when approved. Verify a signed-out visitor can find out who runs the service, whether they can join or pay, and where to get help.
- [ ] **Make source health immediately actionable. Observed on the dashboard and confirmed during the EU sync investigation.** Separate **last successful download**, **publisher last updated**, and **status last checked**. Surface degraded coverage near **New screening**, name the affected source, and explain the effect on results. Rename or clarify **Refresh status** so users know it checks status without fetching new data. Verify a healthy feed, overdue refresh, and failed feed, and confirm that a scheduled failure reaches the responsible operator.

## P1 — Screening and reviewer workflow

- [ ] **Simplify new screening.** Lead with Person/Business, name, and the action. Put the applicable credit cost beside **Run screening**. Collapse optional identifiers and internal references under **Add case details**, but keep existing client-prefilled context visible and editable. Verify both subject types and the client-to-screening path.
- [ ] **Put evidence before the decision form.** The result places the review editor above the evidence it asks reviewers to explain. Lead with coverage and the strongest matches, put identifiers and official evidence together, and put **Record decision** near the evidence. Replace **Human disposition** with plain language. Label similarity as name similarity and ensure it cannot read like confirmed identity. Keep external web searches clearly marked as manual follow-up.
- [ ] **Simplify history actions.** Make the subject name or case reference open the case. Give review state a clear column and put secondary Review/PDF actions behind a menu where appropriate. Check search, presets, empty results, pagination, and whether returning from a case preserves the reviewer’s place.
- [ ] **Replace the dashboard’s Owner metric with work that needs doing.** Keep the role in the organisation context. Use the space for reviews due, unreviewed matches, or a similarly actionable count with a working link to its queue.
- [ ] **Stop defaulting a new client’s next review to today. Reproduced in Safari.** Open **Clients → New client** and observe the prefilled current date. Leave it empty unless a selected template provides an explicit rule. Verify that creating a blank client cannot silently create an immediately due review.
- [ ] **Simplify the client navigation.** The main **Clients** item opens another nav with its own Overview, Clients, Tasks, Monitoring, Configuration, and Integrations, then a client file adds seven tabs. Establish one clear entry into the directory, make queues accessible where users work daily, and rename **Monitoring** to **Reviews due**. Retain access to existing client tabs and direct links. Move the largely informational Integrations page under Sources or Settings until there are actionable connections.
- [ ] **Make client approval prerequisites visible and actionable.** Replace the rules paragraph with a checklist showing what is complete and linking to missing evidence, screening review, tasks, requests, and risk assessment. Explain the independent approver requirement where the user makes the decision. Verify missing requirements and the eligible approval path.
- [ ] **Rename document requests at the point of action.** Use **Create internal request** and make it clear that it creates a workspace follow-up. Verify there is no expectation of email delivery or a client portal. Exercise a synthetic document upload/download and audit trail in a test environment.
- [ ] **Make risk assessments, activity, and templates understandable.** Start risk assessment with the applicable policy, show factors and evidence beside the score, and keep the beta model’s limits clear. In activity, show who did what and when in plain language where actor information is available. In the template editor, show a preview of the resulting client form and distinguish questions from follow-up tasks.

## P2 — Public site, authentication, billing, and settings

- [ ] **Fix homepage clipping and show real product proof. Observed in the browser preview.** The right edge clipped the header signup action and part of the hero card at the reviewed desktop viewport. Reproduce at nearby viewport widths and check mobile, both themes, and keyboard navigation. Reduce repetitive marketing copy. Add an accessible sample result or downloadable sample PDF showing a potential match and incomplete coverage before users register.
- [ ] **Clarify pricing and beta eligibility.** All three public paid plan links lead to the same generic signup. State what is actually available during beta and whether the visitor can pay today. In signed-in Billing, test mode is already disclosed before checkout, but it is buried in a paragraph. Put **Test mode · no live charge** next to the purchase buttons when applicable.
- [ ] **Make login and recovery task-focused.** Reduce promotional copy on login. **Forgot password?** currently tells users to fill the login email first. Give recovery a dedicated email form or inline recovery state with a clear confirmation. Check blank, malformed, and valid email paths without exposing account existence.
- [ ] **Verify signup and confirmation end to end.** Test actual email delivery to a fresh inbox, the allowed redirect, successful confirmation, an expired or used link, and resend. Ensure password requirements, inline feedback, and the server’s actual policy agree.
- [ ] **Separate recovery from signed-in password changes.** The reset page can show its reset form based on any existing session, and an invalid link first appears as if it is being checked. Make recovery require the intended recovery context, present a clear expired-link path, and handle normal signed-in password changes separately.
- [ ] **Fix checkout return states. Reproduced with a missing reference.** Reloading the confirmation URL without a payment reference cannot recover it. Route the user to purchase history or give a direct next step. Reserve retry for a valid pending confirmation. Verify successful, failed, cancelled, and duplicate Stripe test events, including credit grants and purchase history.
- [ ] **Separate account settings by consequence.** Give Profile, Organisation, Members, and Retention/Privacy clear sections with independent save actions and messages. Explain whether changing retention saves a preference or schedules deletion. Verify the owner/admin and ordinary member experiences.
- [ ] **Make public policies customer-facing and accurate.** Review Privacy, Terms, Security, and Sources together. The security page mixes claims that operational controls are verified with a notice that verification is pending. Align claims with documented evidence, explain source and coverage limitations clearly, and provide the right monitored contact. Keep internal launch gates in internal documentation.
